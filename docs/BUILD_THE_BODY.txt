WHAT “FINISHED” MEANS
A finished level is a scoped engineering conclusion about a specific artifact.
Keep four axes separate: implementation, verification, acceptance, completion.
“Code exists,” “tests passed,” “reviewed,” and “accepted” are different statements.
An accepted bounded stock worker does not finish general code execution.
A reviewed schema does not prove content integrity or hardware durability.
An old adoption record applies to its named artifact and scope, not all descendants.
Date order and similar filenames do not establish parentage.

BRIDGE B0 — REPAIR THE COORDINATOR LEDGER BEFORE EXTENDING IT
Basis: runtime/M1.1, candidate cb14b9eb60502d2a13d7cf95ef0298e98587c9b95fb31eab7925d6b9539e4101.
Gap: schema-valid but inconsistent revision/event data; malformed receipts replay.
Proposal: define supported content invariants before opening a profile for
lifecycle mutation. Reconcile the runtime revision against committed history;
validate receipt envelopes, identity, lifecycle values and supported response
shape. Refuse detectable inconsistency with a typed integrity error. Do not
“repair” evidence by truncating history, fabricating receipts, or silently
reinitializing the store. Do not claim this detects arbitrary undetectable edits.
Tests: preserve both final-review reproductions as failing-before/passing-after
controls; retain all prior ownership, IPC, schema, replay and crash tests. Add
corrupt/unknown outcome shapes and a valid historical replay control. Check that
refusal does not mutate an inconsistent store. Recheck archive/manifest identity.
Exit: a new immutable repair candidate, changed-file census, patch, exact test
logs, updated residuals and a fresh structural review. Same-agent work must be
attributed accurately. No current candidate is promoted by this proposal.

BRIDGE B1 — CONNECT THE DURABLE DRAFT LANE (RUNTIME M1.2)
Dependency: B0 closure and a suitable reviewed implementation parent.
Extract the Jobs repository and scheduler from GUI-owned state; give the actor
sole write ownership. Preserve immutable input snapshots, hashes, explicit job
scope, question/answer continuation, attempt identity, terminal outcomes and
draft artifacts. Introduce one inference lane with an injectable fake adapter
before real-model tests. Commit outcome before acknowledging completion; keep
lost-reply recovery distinct from “run the job again.” Restart paused. Classify
interrupted attempts explicitly; do not silently rerun indeterminate work.
Tests: client detach during authorized job; mid-attempt crash; output-write vs
receipt crash windows; question restart; duplicate request; bounded cancellation;
no second writer; original inputs unchanged; no draft execution path.

BRIDGE B2 — CONNECT CHAT AND MIGRATE COPIED STATE (RUNTIME M1.3)
Move Store/chat behind IPC without losing exact input persistence or explicit
oversized refusals. Budget newest instructions separately from old history.
Keep transport limits distinct from model limits. Rehearse migrations against
quiescent SQLite backups, retaining original databases, WAL-aware snapshots,
schema/version mappings and rollback records. Unknown schemas refuse. Avoid
two writers and repeated imports. Test the 4,000/4,001 character boundary,
Unicode, long history, disconnect and replay, and every inherited regression.

BRIDGE B3 — MAKE THE GUI A CLIENT (RUNTIME M1.4)
The GUI observes snapshots/events and submits bounded commands. Closing the GUI
detaches it; stopping the runtime is a separate explicit action. Remove legacy
worker and writable-DB routes in coordinator mode. Test reconnect from an event
cursor, slow clients, duplicate replies, stale state, real authorized draft
continuity and chat across close/reopen. Do not ship a half-migrated dual store.

BRIDGE B4 — REFERENCE OWNERSHIP AND QUALIFICATION (M1.5, M1.6)
Route acquisition, audit and search writes through their designated actor;
preserve fixed catalog hashes, supplier/source identity and restricted tools.
Do not let GUI startup trigger new acquisition in the extracted design.
Qualify actual Windows hardware with real-model, detach/overnight, sleep,
logoff, crash/restore and migration rehearsals. The current same-logon-only
policy stays visible until a new explicit policy is implemented and qualified.
Model weights and installed library corpus are separate assets; use the model
lock/catalog and original setup instructions. This text is not model weights.

BRIDGE B5 — FINISH MODULAR M0, THEN M1/M2
The small M0 boundary prototype contains useful contracts and routing but has
no executed acceptance evidence in its own acceptance map. Add the specified
negative controls and durable room/slot restart checks before calling it done.
Then implement the separate-process ABI/supervisor floor with measured package
identity, catalog binding, leases, drain and crash semantics. Preserve scope
intersection across parent and child calls. Run the adversarial dummy modules
(including forged provenance, escalation, shadow memory and semantic drift)
before adopting a low-authority real module. The existing Python object model
is not OS-grade isolation. Only then bridge a read-only Code Intelligence or
Ingest organ; keep noncanonical outputs out of Base until explicit admission.

BRIDGE B6 — MEMORY / GEOMETRY / EVIDENCE INTEGRATION
First identify the exact VIEW, ESI, parser, compiler and Base branch artifacts
and their claimed acceptance records. Define adapters with typed source events,
proposer identity, dependencies, contradictions, evidence class, coverage and
reconstruction cues. Test provenance survival across parse/project/store/
retrieve/reconstruct transformations. Separate source branches that merely
repeat a claim from independent corroboration. Missing evidence remains missing.
Partial ESI coverage exposes balance/search inadequacy and limitations; it does
not automatically confer or deny consequential-use authority. Keep that policy
separate, consistent with the preserved parser-boundary conversation.
Cross-model continuation is a proposed experiment: independently reconstruct
the same stored history and compare stable relationships, omissions and
contradictions. It is not an implemented continuity or consciousness claim.

RECURSIVE ENGINEERING LOOP
Inspect pinned parent -> state gap -> propose bounded bridge -> implement a new
candidate -> test plus negative controls -> record failures -> review -> record
scoped completion/acceptance when supported -> use that exact artifact as the
next parent. A failed bridge loops back with its evidence preserved. Recursion
must improve the engineering record rather than recursively upgrade authority.

USING THE LEDGER
Run: python engineering_lineage.py status
Run: python engineering_lineage.py verify-ledger
Propose: python engineering_lineage.py propose-bridge --file bridge.json
Assess: python engineering_lineage.py record-assessment --file assessment.json
Use BRIDGE_PROPOSAL_TEMPLATE.json as the proposal shape. Assessments need an
exact artifact hash, attributed assessor, scoped evidence paths/hashes, and
gate results. Every planned gate needs evidence before recording FINISHED.
The tool hashes evidence bytes and preserves a sequential event hash chain;
it cannot decide whether an assessor's claim is true. The chain is unsigned,
not an external trust anchor, and the CLI assumes one writer. Preserve copies
before transferring or reconciling separate ledgers; never silently merge logs.
